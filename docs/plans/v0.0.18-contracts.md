# v0.0.18 contracts: organizations, roles, and invitations

Status: Step B of Phase 17 (see `docs/plans/README.md`). This document defines the flows and rules that later steps (C–E) implement. Where a rule is not yet enforced in code, the **Status** line says so.

## Identity and tenancy

- A **user** is a global identity (`nexa_users`). Login is by email and password.
- An **organization** is a tenant (`nexa_tenants`). A user may belong to many organizations through `nexa_organization_memberships`.
- Each organization has its own role assignments (`nexa_role_assignments`) and per-organization role memberships (`nexa_user_role_memberships`).
- The active organization is part of the session. The server resolves it from a membership it has verified. Callers cannot choose a tenant by sending a header.
- `SYSTEM_TENANT_ID` is an internal scope for the platform. It is not offered as a customer organization.

## Roles

Each organization has exactly four system roles. Their ids are fixed.

| Role | Intent |
|---|---|
| `owner` | Full control of the organization, including managing members and the organization itself. |
| `admin` | Everything `owner` can do except organization settings (`org:manage`), and except changing owners. |
| `member` | Works with modules and records; cannot change definitions or members. |
| `viewer` | Read-only access to modules, definitions, and records. No reports. |

Removed: `editor` and `administrator`. Migration `0009` has not been applied anywhere, so these roles were never stored and no data migration is needed.

Permissions (`packages/engine/permission/index.ts`) are default-deny. Unknown roles grant nothing.

| Permission | owner | admin | member | viewer |
|---|---|---|---|---|
| `module:read` | yes | yes | yes | yes |
| `module:write` | yes | yes | no | no |
| `definition:read` | yes | yes | yes | yes |
| `definition:write` | yes | yes | no | no |
| `record:read` | yes | yes | yes | yes |
| `record:write` | yes | yes | yes | no |
| `workflow:transition` | yes | yes | yes | no |
| `action:execute` | yes | yes | yes | no |
| `automation:manage` | yes | yes | yes | no |
| `report:read` | yes | yes | yes | no |
| `report:manage` | yes | yes | yes | no |
| `member:manage` | yes | yes | no | no |
| `org:manage` | yes | no | no | no |

Notes:
- `member:manage` covers inviting, changing roles, and removing members, subject to the rules below.
- `org:manage` covers organization settings and is owner-only.
- The matrix above matches the code after Step B and keeps the behavior from earlier phases. Phase 12 made `report:read` and `report:manage` default-deny for viewers, so `viewer` has no report permissions.

**Status:** matrix is defined in code in Step B. Routes that check `member:manage` and `org:manage` are added in Step E.

## Organization signup and creation

- **Signup** (`POST /v1/auth/signup`): creates a global user, a new organization, and an `owner` membership in one transaction, then starts a session. Disabled when `NODE_ENV=production` until email verification exists.
- **Create another organization** for an existing user: the user becomes `owner` of the new organization. Each organization is its own tenant.
- **List** (`GET /v1/auth/organizations`): returns only memberships that are active, on active organizations.
- **Switch** (`POST /v1/auth/organizations/select`): the caller must already be an active member. Otherwise the server responds 403 and does not change the session.

**Status:** signup and list/switch exist. Creating a second organization for an existing user is added in Step D.

## Invitations

- An owner or admin (`member:manage`) creates an invitation with an email, a role, and an expiry.
- The role must be one of `admin`, `member`, or `viewer`. **An invitation cannot grant `owner`.**
- The server generates a random token, stores only its hash (`token_hash`, unique), and sends the token to the invitee in a link. The raw token is never stored and is shown only once.
- Expiry is required. The default is 7 days. Expired invitations cannot be accepted.
- **Accept**: the caller must be signed in with the same email as the invitation (case-insensitive). It fails if the invitation is expired, revoked, or already accepted. On success it creates an active membership with the invited role.
- **Revoke**: sets `revoked_at`. A revoked invitation cannot be accepted.
- A token is single-use. Using it twice returns the same failure as an invalid token, so an attacker learns nothing about which invitations exist.

**Status:** tables and endpoints are added in Steps C–E. Email delivery is not part of this phase in production; development logs the accept link.

## Membership changes

- **Change role**: requires `member:manage`. An admin cannot assign or change `owner`. Only an owner can make another user an owner, and the invitation rule above still applies to new members.
- **Remove member**: requires `member:manage`. Removing a member revokes their memberships in that organization.
- **Last owner**: the system never leaves an organization without an active owner. A change or removal that would leave zero owners returns 409.
- **Self-demotion**: the same last-owner rule applies. Users can leave an organization only if another owner exists.

**Status:** enforced in Step D (repository) and Step E (routes). Until then, the matrix alone does not protect these operations.

## Authorization for management endpoints

- Management endpoints (members, invitations, organization settings) take their tenant only from the verified session.
- The `x-tenant-id` header is ignored for every endpoint. Step E adds a test that proves this.
- Anonymous requests return 401. Authenticated users without the required permission return 403.

## Error codes

`FORBIDDEN`, `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `INVALID_INPUT`, `AUTH_CONFLICT`, and `ORGANIZATION_CONFLICT` exist today. `LAST_OWNER` and `INVITATION_NOT_FOUND` are planned for Steps D–E.


| Situation | Status | Code |
|---|---|---|
| Not signed in | 401 | `AUTH_REQUIRED` |
| Wrong email or password | 401 | `INVALID_CREDENTIALS` |
| Signed in, lacks permission | 403 | `FORBIDDEN` |
| Not a member of target organization | 403 | `FORBIDDEN` |
| Invalid input | 400 | `INVALID_INPUT` |
| Email already registered / slug taken | 409 | `AUTH_CONFLICT` / `ORGANIZATION_CONFLICT` |
| Would leave organization without an owner (planned) | 409 | `LAST_OWNER` |
| Invitation invalid, expired, revoked, used, or email mismatch (planned) | 404 | `INVITATION_NOT_FOUND` |

`INVITATION_NOT_FOUND` is used for all invitation failures so the response does not reveal which case applies.

## Out of scope for v0.0.18

- Email verification and production signup (signup stays disabled in production).
- A real email transport for invitations.
- Per-user custom roles. Only the four system roles exist.
