Rule: one phase per version branch (`v0.0.1`, `v0.0.2`, ...), in order. Phase 0 uses `v0.0.1`; each later phase increments the patch version once. Do not begin a subsequent phase or create its branch until explicitly requested.

## Phase 22 — Own component library in `packages/ui` (complete)

Source design: `D:\project\mockup\nexa.figcraft` (a zip holding `document.json`; readable). The mockup was built on Nuxt UI tokens (`--ui-bg`, `--ui-primary`, ...), primary green/emerald, neutral slate, Light and Dark modes, so Tailwind theme variables can mirror it one-to-one.

### What the mockup contains
- **Design tokens** (Figma variables and `Nexa/*` styles): Nuxt UI Colors, Primary (Green/Orange/Sky/Teal), Neutral (Gray/Neutral/Slate/Zinc), Tokens (Dark/Light), Font (DM Sans/Public Sans), Secondary, Radius (2/4/6/8px). Text styles Regular/Bold/Mono, 11–64px. The styles currently use Leelawadee UI; the mockup notes to switch to Noto Sans Thai.
- **Component library** (page `Component`, 20 groups): Logo, Button (Primary/Secondary/Neutral/Ghost/Danger × default/leading/trailing icon/sm), IconButton, Badge (Success/Info/Warning/Error × plain/dot/icon), Input, Select, Textarea, Switch, Checkbox, Radio, Avatar, Kbd, Chip, Alert, Tab, Segment, NavItem, Card, Modal, Toast. A Dark preview frame exists.
- **Field renderers** (page `Fields`, Light and Dark): per field type, states default/focus/error/disabled/readonly/loading and displays table/detail/kanban.
- **Screens** (Light and Dark pages): Login (auth, signup, invitation, select organization), Admin (Builder: modules, lifecycle, entity/formula/relation designers, view/form designers, workflow, automations, reports, dashboards, permissions, package; Admin: organization, members, roles, audit, events, operations), User (home, command palette, notifications, settings, table/kanban/calendar/gallery, empty/no-results/loading/error, record form/detail/conflict 409, CSV import, dashboard, error pages, offline, tablet 768, mobile 375).
- **Icons**: about 2150 Lucide-named 24px components (use `lucide`-style icons; do not draw them by hand).

### Steps (each a separate commit, in order)
1. **Foundation**: remove the `@nuxt/ui` dependency from `packages/ui`; Tailwind v4 theme with CSS variables for the tokens above (Light and Dark), Noto Sans Thai + Inter, radius scale, a `cn()` helper; keep the Nuxt layer shell and playground so `extends: ['@nexa/ui']` keeps working.
2. **Base components**: Button, IconButton, Badge, Chip, Avatar, Kbd, Logo, Card, Alert, Toast, Modal, Tab, Segment, NavItem, and the form controls Input, Textarea, Select, Checkbox, Radio, Switch, each with the variants and sizes the library shows.
3. **Field renderers**: input and display renderers for every `FieldTypeSchema` value, with the six states and three displays; reference fields take a `loadOptions(search)` prop so `packages/ui` never imports the SDK.
4. **Composites** (only when a screen needs them): table, pagination, form, detail, command palette, kanban. View/form definition persistence stays out of scope.
5. **Gate**: Vitest per component (props, states, keyboard), a test that scans `packages/ui` for hardcoded colors, Light/Dark contrast check, `nuxi typecheck`, ESLint, playground build; verify visually in the playground against the mockup.

### Rules for this phase
- `packages/ui` takes data as props and never calls the SDK; business rules stay in `engine`/`db`.
- Components use only token utilities (no raw hex), support Light and Dark, and are keyboard accessible with correct ARIA.
- Decided 2026-10-16: overlays use Reka UI; `packages/ui` is a plain Vue 3 + Tailwind v4 package (no Nuxt layer, no `@nuxt/ui`).
- Out of scope: reassembling `apps/web`, file upload, charts, and new backend endpoints. Screens in the mockup are reference for later phases; this phase ships components only.

## Phase 24 — Bring a module into a tenant (complete)

Requested on 2026-10-21, on top of the green gate. Two phases had left the same path unfinished, and the note above named it: Phase 13 shipped the package repository with `importPackage` written, transactional and integrity checked, and no route ever called it; Phase 15 shipped three metadata templates that nothing could reach. A package could leave a tenant but not come back, and a template was metadata on disk.

**The import route.** `POST /v1/modules/:moduleId/package/import` takes a `ModulePackage` and lands it as a draft module, in one transaction with the integrity validation and the audit row the repository already had. The server owns the identity of what lands — the tenant, the owner, the timestamps, the status and the module id. A package carries the identity of the tenant it was exported from, and that copy is not authoritative, so it is normalised before it is stored rather than refused.

Two refusals are the route's own. The manifest has to agree with the module id in the URL. And the definition ids of one kind have to be unique among themselves: a definition id is unique per module, not per entity, and a repeat would surface as a database error rather than an answer.

**The template route.** `POST /v1/modules/:moduleId/from-template` installs one of the built-in templates. The template is converted into a module package and imported through the same path, so a template lands as a draft module with its entities, fields and relations. The tenant chooses the module id and may name the module; the template decides the content.

**A detail the templates forced.** A metadata template nests its fields inside its entities, while a module package keeps the fields in one flat list. The inventory template has a field called "name" on both its product and its warehouse entity, so imported as written it collided with itself on the primary key and the import died on a database error. The converter namespaces a field's id with the entity it belongs to and leaves the name alone, so the UI still shows "Name" and the record data keys stay unique.

**The template shape is a schema now.** `MetadataTemplateSchema` in `packages/meta` makes it a first-class thing: the converter parses with it, and the template test asserts against it instead of validating the three templates entity by entity. The fields inside a template go through the same structural rules a field creation input follows, so a template cannot carry a field the API would refuse to create.

No migration: the metadata definitions table already carries the kind discriminator, and the module and audit tables already exist. The acceptance suite installs the CRM template, walks it through the lifecycle to enabled, records an account and a contact, and reads the account back.

**Not in this phase.** Views and forms are still schema only: the package's `views` and `forms` slots round-trip through export and import, but nothing can create or list them, they are excluded from the integrity validation, and the Phase 20 renderers that would have consumed them were deleted in Phase 21. ## Phase 25 — The three gaps the backend still had (complete)

Requested on 2026-10-21, as the three pieces the note above named. All three were schemas or intentions with no way to reach them.

### Views and forms as definition kinds

A view and a form were schemas with no way in and no way out: they had no module id, no repository, no route, and the Phase 20 renderers that would have consumed them were deleted in Phase 21. The package's `views` and `forms` slots round-tripped through export and import, but nothing could ever put a view into a package to begin with.

No migration: the metadata definitions table already carries a kind discriminator, so a view and a form are rows in the same table with their own kind. The module schema, the package round trip and the integrity validation learn about them, and the schemas gain the module id and the create and update input schemas the other definition kinds have.

The validation is the part that matters. A view or a form names an entity that has to exist, and the fields it names have to be fields of that entity: a column pointing at a field of another entity would render an empty column forever. An entity has one default view, because two of them leave the choice of which one to open ambiguous.

The permissions did not change. A view is metadata about records, not a separate kind of access, so the routes read and write on `definition:read` and `definition:write` — the same ones the workflows and actions use. The role matrix is untouched, and a viewer still cannot write one.

### Scheduled automations that actually fire

A scheduled trigger was in the schema since Phase 11 and the engine declined every one of them. The cron expression is now matched against the instant the schedule is evaluated in, in the trigger's own time zone, so a schedule written in local time keeps its meaning across a daylight-saving change. The expression is the five-field form, with ranges, lists and steps, and when the day of month and the day of week are both restricted a day matches if either field matches, the way cron has always worked.

The scheduler walks the tenants, finds the automations whose schedule matches the minute, and enqueues one job per automation. The work goes through the same durable outbox as every other automation, so a crash between the schedule matching and the delivery leaves the job pending instead of losing the run. The dedupe key carries the minute, so the same automation cannot be enqueued twice for one minute however often the scheduler runs. A minute that passes while the scheduler is down is not made up for: a schedule that missed its minute is late, not repeated.

### Permission definitions as a kind

A permission definition was a schema with no repository and no route, so a module could say nothing about who may do what inside it. It is a definition kind like the rest, and the package gained a permissions slot so it travels with the module. A permission that names a resource the module does not have grants nothing, so it is refused rather than stored: the entity, the field or the action it points at has to exist.

What it does not do yet is enforce anything. The platform's role matrix in `packages/engine/permission` is still what the engine checks, and the module's own permission definitions are stored, readable and exportable but not consulted. Turning them into an access decision is a separate piece: it touches the permission model itself, which is the most security-sensitive code in the repository.

**The import route now rewrites the module id of the definitions.** A package names the module it was exported from; the definitions belong to the module they are imported into. The entities had the same problem and were carrying the exporting module's id inside their definition; the views, forms, workflows, actions, automations, reports, dashboards and permissions now get the same treatment.

The views and forms are exercised over HTTP: create, list, filter by entity, read, update and delete; the references are refused when they name something the module does not have; an entity has one default view; a viewer cannot write a view; and a package round trip carries the views, the forms and the permissions. ## Phase 26 — Enforce the module's own permission definitions (complete)

Requested on 2026-10-21, the piece the previous phase left open. The permission definitions were a kind: stored, readable, writable, exported and imported. Nothing consulted them, and the platform's role matrix was the only thing that decided access.

### The platform's matrix is the ceiling

A module can narrow what a role may do, never widen it. That direction is the whole design. A module is the tenant's own, and its definitions are authored by whoever holds `definition:write`; if a module could widen the platform's grant, a module owner could hand a viewer write access to the records. So the check is two gates and both have to pass: the platform's matrix, exactly as it was, and then the module's own definitions for the principal's roles.

`hasModulePermission` sits next to `hasPlatformPermission` in `packages/engine/permission`. A definition covers a request when its resource is the module itself, or when it is the same kind of resource and either names no id or names the same one. The action has to be in the actions of at least one covering definition. When no definition of the principal's roles covers the resource, the module says nothing about it and the platform's answer stands, which is what keeps a module without permission definitions behaving exactly as it did before.

### Where it is consulted

The record routes narrow by the entity the records belong to and the method that touches them: a read, a create, an update, a delete. The relation link routes change a record, so they count as an update. The package routes narrow by the module itself, so a definition that covers the whole module decides and one that names an entity does not.

The definition routes are left on the platform's `definition:read` and `definition:write`. Who may design a module is the platform's business; who may see its data is the module's. That also removes the foot-gun of a module narrowing the very routes an owner would need to undo the narrowing.

### Policy is not schema

A module's schema is frozen once it is live, because the records depend on it. Its permission definitions are policy: no record depends on them, and a tenant has to be able to narrow access to a running module, which is exactly when narrowing matters most. They therefore get their own mutation path, one that takes the module lock and writes the audit trail but does not refuse an enabled module. They are still checked against the module, so a permission naming an entity the module does not have is refused rather than stored.

This was found while writing the tests rather than by design: the first run of the permission creation against an enabled module came back with `Definitions cannot be edited while the module is enabled`, and a feature that cannot change the access of a live module is not a feature.

**Gate for this phase.** From a shell that still exports `NODE_ENV=production`: lint 0 errors and 0 warnings; `pnpm typecheck` 0 errors across 15 tasks; the full test suite passes; `pnpm build` passes; `pnpm db:check` passes with 12 migrations and 16 tables, unchanged. The enforcement is exercised over HTTP with a member of the tenant: a module that lets the member read one entity refuses the member's write on it and leaves the entities it says nothing about alone, a module that hands a viewer a write still does not get one, a module with no definitions behaves as before, and the owner can widen its own narrowing again.

**Not in this phase.** The `condition` on a permission definition is stored and not evaluated: it is a per-record condition, and a list request has no record to weigh it against. The `field` and `action` resources are stored and matched exactly, but no route names one yet. The definition routes are not narrowed. Nothing renders a view or a form yet: the Phase 20 renderers were deleted, `apps/web` is not reassembled, and `packages/ui` is a component library with no API calls.
